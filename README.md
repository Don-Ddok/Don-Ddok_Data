# Don-Ddok_Data

돈독(Don-Ddok) 팀의 **데이터 전처리·분석 코드** 저장소입니다. 문서·회의록은 [Don-Ddok_Docs](https://github.com/Don-Ddok/Don-Ddok_Docs)를 참고하세요.

---

## 0. 절대 원칙 — 원본 데이터는 절대 올리지 않는다

이 저장소는 **공개(public)** 입니다.

- **iM뱅크 제공 법인 익명데이터(`.xlsx`)와 거기서 파생된 원본 수준 파일은 어떤 브랜치에도 커밋하지 않는다.** 익명화되어 있어도 은행이 비공개로 제공한 자료다.
- 커밋해도 되는 것은 **공개 출처(관세청·KOSIS·한국은행 등)에서 받은 외부 데이터**와 **코드**뿐이다.
- 실수로라도 올라가지 않도록 저장소 루트의 `.gitignore`가 원본 파일명·확장자를 걸러낸다(2절 참고). 커밋 전 `git status`로 스테이징된 파일을 반드시 확인한다.
- 결과물(표·그림)에 법인을 특정할 수 있는 정보(법인ID, 상호, 정확한 소액 거래금액 등)를 그대로 노출하지 않는다.

**실수로 올렸다면**: 즉시 알리고 해당 커밋을 되돌린다. `git rm`만으로는 히스토리에 남으므로 팀원과 상의해 히스토리 재작성 여부를 정한다.

## 1. 폴더 구조

```
/data
  /external          # 공개 출처 외부 데이터 (커밋 가능) — 관세청 수출입, KOSIS 생산지수, ECOS BSI·금리·환율
  /raw                # 은행 원본 데이터 두는 자리 — .gitignore로 제외, 로컬/드라이브에만 존재
  /processed          # 전처리 완료된 분석용 테이블 — 기본적으로 제외(용량·민감도), 필요 시 개별 협의
/notebooks
  /01_preprocessing   # 전처리·변수 생성
  /02_diagnostics     # 0단계 결합 검증, 변수 정의 검증(소진율 등), EDA
  /03_analysis        # 정상성·시차탐색·패널회귀·매칭
  /04_robustness      # 강건성, 위약검정
/src                  # 노트북에서 반복 쓰는 함수 (전처리, 회귀, 시각화 유틸)
/outputs
  /tables             # 산출물 표 (csv/md)
  /figures            # 그래프 (png/svg)
docs/                 # 데이터 명세서, 변수 정의서 등 코드repo에 딸린 짧은 문서
README.md
.gitignore
```

- `/data/raw`, `/data/processed`는 폴더 자체는 두되(`.gitkeep`) 안의 실 데이터는 올리지 않는다.
- 이미 확보한 외부 데이터(`production_index_industry.csv`, `production_index_region.csv` 등)는 `/data/external`로 옮겨 올린다.

## 2. `.gitignore` (최소 기준)

```gitignore
# 은행 원본 데이터 — 절대 커밋 금지
*.xlsx
*.xls

# 은행 데이터에서 파생된 중간 파일(회사 단위 값 포함) — 커밋 금지
*.parquet
*.feather
*.pkl
*.db
*.sqlite
/data/raw/**
/data/processed/**
!/data/raw/.gitkeep
!/data/processed/.gitkeep

# Python
__pycache__/
*.pyc
.ipynb_checkpoints/

# 환경
.env
```

`*.xlsx`를 전체 차단하므로, 외부 데이터를 엑셀로 받았다면 `/data/external`에 넣기 전에 CSV로 변환한다(어차피 분석은 CSV가 다루기 쉽다).

은행 데이터에서 만든 중간 파일은 parquet로 저장하고(자료형 유지, 로컬 전용), 팀에 공유할 **집계 결과표**만 CSV(`utf-8-sig`)로 `/outputs/tables`에 올린다. 집계표에도 법인ID나 회사 단위 값이 들어 있으면 올리지 않는다.

## 3. 브랜치 전략

Don-Ddok_Docs와 동일한 원칙을 쓰되 코드 성격에 맞춘 타입을 쓴다.

| 브랜치 타입 | 용도 | 예시 |
|---|---|---|
| `main` | 항상 실행 가능한 상태 | `main` |
| `feat/*` | 새 분석·전처리 단계 추가 | `feat/lag-crosscorr` |
| `fix/*` | 버그·계산 오류 수정 | `fix/winsorize-bounds` |
| `data/*` | 외부 데이터 추가·갱신 | `data/kosis-index-update` |
| `docs/*` | 이 저장소 안의 문서(명세서 등) | `docs/variable-spec` |

- `main`에 직접 push하지 않는다. 작업은 브랜치를 파서 PR로 병합한다.
- 병합 후 브랜치는 삭제한다.

## 4. 커밋 메시지 컨벤션

```
<type>: <내용>
```

| type | 설명 |
|---|---|
| `feat` | 새 전처리·분석 코드 추가 |
| `fix` | 계산/로직 오류 수정 |
| `data` | 외부 데이터 추가·갱신 |
| `refactor` | 동작 변경 없는 코드 정리 |
| `docs` | 이 저장소 안의 문서 추가·수정 |
| `chore` | 폴더 구조, 설정, 의존성 등 |

예시: `feat: 시차 0~6개월 교차상관 계산 추가`, `data: 대구·경북 수출액 CSV 갱신(2025.12까지)`

## 5. 노트북·코드 규칙

- 노트북 파일명은 **번호 + 내용**으로: `01_preprocessing_export_exposure.ipynb`처럼 실행 순서를 알 수 있게 한다.
- 노트북 상단에 실행 환경을 적는다: Colab 기준(`drive.mount('/content/drive')`, 경로는 `/content/drive/MyDrive/...`)인지 로컬(`python`, Windows) 기준인지 명시한다.
- 반복해서 쓰는 함수(전처리, 회귀 실행, 표 만들기)는 노트북에 복붙하지 말고 `/src`로 뺀다.
- 커밋 전에 노트북 출력(특히 원본 데이터의 실제 값이 찍힌 셀)을 확인한다. 필요하면 `jupyter nbconvert --clear-output`으로 출력만 지우고 커밋한다.
- 코드는 다른 팀원이 그대로 실행해서 같은 결과가 나와야 한다. 랜덤 시드, 파일 경로, 필요한 라이브러리 버전을 노트북 상단이나 `requirements.txt`에 적어 둔다.
- 회귀·검정 결과 표는 숫자만 던지지 말고 셀 마지막에 한두 줄 해석을 남긴다. 세 보고서(방향성 문서·중간 보고서·기본 보고서) 사이에 숫자가 어긋난 전례가 있으니, **어떤 표본·전처리·모형 버전에서 나온 숫자인지**를 표 옆에 반드시 적는다.

## 6. PR 규칙

- 제목: `type: 내용 요약` (예: `feat: 국소투영 패널회귀 h=0~12 구현`)
- 본문에는 (1) 무엇을 추가/변경했는지, (2) 어떤 데이터로 돌렸는지, (3) 결과가 이전 버전과 다르면 무엇이 왜 다른지를 적는다.
- 원본 데이터가 포함되지 않았는지 PR 작성자가 diff에서 먼저 확인한다.
- 병합 방식은 Squash and Merge로 통일한다.

## 8. 외부 데이터 검증 규칙

출처가 적혀 있어도 값은 따로 확인한다. 외부 데이터를 `/data/external`에 올리거나 분석에 쓰기 전에 아래를 지킨다.

1. **원자료와 대조**: 발표 기관(ECOS·KOSIS·K-stat 등)에서 같은 계열을 직접 받아 값이 일치하는지 확인한다. 증감률 열이 있으면 원래 값으로 다시 계산해 맞는지도 본다.
2. **이상 신호 확인**: 같은 값이 여러 달 반복되거나, 증감률이 0으로 찍히거나, 0인 계열(미공표)이 있는지 본다.
3. **출처 기록**: 파일에 통계표 코드, 계열 이름, 수집일을 열이나 파일명으로 남긴다.
4. **오류를 찾으면**: 원래 파일은 덮어쓰지 않고, 원자료로 새 파일을 만든 뒤 팀에 알린다. 이미 그 파일을 쓴 분석이 있는지 확인한다.
